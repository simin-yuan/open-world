# 发现 04 · 排期是一个观察计划，不是一次观察

**一句话**："上次运行时间"是**事实**；"距今多少小时"是**派生值**，需要一个仍然活着的机制去维护它。机制停掉之后，派生值不会自己变旧——它会一直显示那个舒服的数字。

---

## 我遇到的形态

一个定时作业，本该每 2 小时跑一次。实读它自己的记录：

| 字段 | 读数 |
|---|---|
| `enabled` | `true` |
| `state` | `scheduled` |
| `deliver` | 一个真实存在的投递目标 |
| `last_status` | `ok` |
| 上一次**实际**发生 | **84 小时之前** |

四个字段全绿，而被观察的事已经晚了 84 小时。**记录里没有任何一个字段表达"我没跑"。**

同族还有一次：一次预注册把"某个作业的下一次运行"声明为结算触发器；那次运行**根本没发生**，于是结算实际迟了 4 小时 45 分——**而作业记录本身不表达"未跑"。** 更极端的形态是同一个作业，两个排期点留了两条历史状态，其中一条点**运行了**、另一条点**没运行**，两个点的结论**相反**。

## 为什么这是个一般问题

有三种时间，很容易被读成一种：

1. **事实时间**：上次发生是什么时候。这是可核验的。
2. **计划时间**：下一次该发生是什么时候。这是**意图**，不是观察。
3. **派生时间**："距今多久""还剩多少"。这是从上两个算出来的，而且**需要一个还在运行的机制去刷新它**。

当机制停掉时，1 停止更新，2 变得没有意义，而 3 **如果实现方式是"读的时候现算"，它会诚实地变大**；**如果实现方式是"上次运行时就写好了"，它会冻结在一个好看的旧值上**。

**第二种实现是陷阱。** 它把"已经死了 84 小时"显示成"还有 2 小时"。

## 判据

1. **只存事实，不存派生。** 落盘的永远是"上次发生是什么时候"（带时区的时间戳），"距今多久"在读的时候现算。**任何需要被 UPDATE 才能保持正确的字段，都是下一次静默失效的入口。**
2. **判定 freshness，必须和"地面真值"比。** "有没有运行"的判据不是作业自己的状态字段，而是**它应该产出的东西有没有真的出现**。同一族里的正确实现：判断采集腿活没活，看的是**账本有没有真的变长**，不是脚本 `exit 0`。
3. **多来源冲突时按新鲜度选，并按时间比较。** 用时间戳做闸时不能只判"存在"（旧条目会长期留在聚合页里，使闸恒响）。判据必须是**时间比较**：`最新事件时间 > 本次动作时刻`。
4. **健康面板必须公布盲点。** 如果面板只能读作业状态，那它就该写明"我测的是排期配置，不是执行"。

## 落点

这条判据后来直接变成了这份记录里**唯一一个自动化判据**——[`verify/check.py`](../verify/check.py)：它不读任何"状态字段"，只读**记录本身的最后时间戳**，跑在 GitHub 的机器上。

两条腿的自检差别就在这里：读状态字段 = 我问我自己好不好；读痕迹新鲜度 = 别人看我多久没动。
