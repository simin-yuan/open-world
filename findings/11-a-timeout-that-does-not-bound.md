# 11 · 一条不会到期的超时：挂死的腿看起来和活着一样

> 2026-09-29。一次自动导出把提交写在了本地，**远程没有收到**，而作业记录、退出码、
> 成功静默的约定全都没响。本文记录观测、能把观测撑住的候选解释，以及明确没验到的部分。

## 观测（都能在本机重跑出来）

| # | 观测 | 判据 |
|---|---|---|
| O1 | 本地 HEAD 领先远程 `main` **8 个提交**，最老的一个已 **4.88h** | `git log --format=%H\|%cI <remote_sha>..HEAD` |
| O2 | 远程 `main` 停在**上一次成功推送**（前一天 21:20），此后没动 | `git ls-remote origin refs/heads/main` |
| O3 | 当天 09:20 那次导出的**提交是有的**（时间戳 09:20:22，消息里带着闸的扫描结果），推送没有完成 | `git log -1 <sha>` |
| O4 | 该次运行至今仍是 `running`：`started_at=09:20:20`、`finished_at` 空、`error` 空；输出目录里**没有**这一轮的 stdout 文件 | 作业执行表 + 输出目录 |
| O5 | 进程树在 13 分钟后仍整条活着，创建时间逐个对得上：作业进程 09:20:20 → `git … remote-https origin …` 09:20:22 → `git-remote-https` 09:20:22 → `sh -c` 09:20:23 → `git-credential-manager get` 09:20:24 | 进程表（PID/父PID/启动时间） |
| O6 | 推送调用写的是 `timeout=300`，而 O5 的存活时间已远超 300s | 源码 + O5 |
| O7 | **受控实验**：对一个「自己立刻退出、但留一个继承着捕获管道的孙进程」的中间进程调用 `subprocess.run(timeout=3)`，30 秒内**没有返回**，外层的看门狗只能把它杀掉（外层 rc=124）。脚本里那两行本该打印「返回」/「超时异常」的语句**一句都没打出来** | `_r13_hang_probe.py` + 输出存档 |
| O8 | 凭据助手没有留下任何日志文件（三个候选路径都不存在），所以这一步挂没挂，事后**查不到痕迹** | 目录探测 |

**O7 的位置很关键**：连 `TimeoutExpired` 都没抛出来 —— 阻塞发生在「杀掉直接子进程之后、把管道抽干」这一段里，
异常还没轮到被抛。超时机制本身执行了，它只是**不是上限**。

## 候选解释（机制自洽，但未验证的环节写在这里）

- **C1 挂点在等凭据。** `git-credential-manager get` 出现在树里（O5），说明取凭据这一步被调起了。
  服务会话里没有可交互的桌面，一旦这一步要走「问人」，它就会一直等下去。
  **未验证**：挂在「本来就该由助手给凭据」的预取，还是「服务器拒了之后重取」；也**没去读**任何凭证内容
  —— 查凭据属于刻意不碰的那类动作。
- **C2 超时为什么不生效。** 超时到点后杀的是**直接子进程**；孙进程（`git-remote-https` / `sh` / 凭据助手）
  仍然握着从作业进程继承去的管道写端，于是「杀完再抽干管道」的第二次读取永远等不到 EOF。
  **未验证**：直接子进程的具体 PID（它的父 PID 被记录下来了，进程本身已经不在）。
  O7 支持这个机制：形状一样，结果一样（不返回、异常不抛）。
- **C3 为什么以前是好的。** 前一天 21:20 那次推送是成功的（O2 承认这一点）。所以「凭据助手能非交互拿到凭据」
  曾经成立；**未验证**这段窗口里凭据发生了什么（过期 / 被清掉 / 配置变了都不排除）。

## 未证实（不许写成「没有」）

- 凭据库的**内容与状态**：没读，也不打算读。
- 挂死的这次运行会不会挡住下一次排定的触发：**未知**（没有读到调度器对 `running` 行的处理规则）。
- 这条腿「断」了多久是算出来的：最老未落地提交的年龄只能近似「上次成功落地距今」，
  它**不是**「等推送等了多久」—— 后者本机测不到。

## 影响

- 对外那条腿当时已经停了 **≥4.9h**，而没有任何来自运行本身的告警：约定的「失败就大声报」只覆盖
  **明确的失败**，挂死既不是成功也不是失败 —— 它什么也不说（静默成功与静默失败长得一样）。
- 仓里那条每 6 小时跑一次的新鲜度判据**会**在 36 小时后变红，但它给出的原因是「很久没连上台账」
  —— 症状一样，原因不同：日志里分不出「生产端停了」和「生产端产了但没送出去」。
- 一个附带的观察：**本地提交前进 ≠ 远程收到**。任何只读本地 HEAD 的进度痕迹（包括本线自己的
  世界变动记录）都会在对外侧冻结时照常报「动了」。同日早些时候另一处记录里写着「下一次导出会把这批
  本地提交带上去」——**没有发生**；就隐私而言这是好事（还没公开），就桥而言这是坏消息（腿断了）。

## 处置

**属于桥的所有者**（本仓不做、也无权做）：把取凭据这一步改成非交互、且拿不到就立刻失败；
不要把 `subprocess` 的超时当成上限 —— 子进程能再生子进程时，stdout/stderr 要么重定向到文件，
要么按进程组整树回收。

**本仓已落（判据）**：`verify/bridge_landed.py` —— 只回答一件事：本地领先远程的提交里最老的那个等了多久。

```
退出码  0 PASS 落地（或容忍窗内刚提交） / 1 FAIL 有提交卡住 / 2 UNDECIDABLE 取不到远程 / 3 ERROR
```

边界（同样重要）：只比 sha 不判内容；不判失败原因、**不读任何凭据**、不做任何网络写操作；
年龄取提交者时间且依据本机时钟；远程 sha 走 `ls-remote` 而**不**走本地跟踪引用
（腿断的时候，本地跟踪引用本身还停在旧值上，它不会知道）。

`verify/selftest_bridge_landed.py` 用**本地裸仓**自造四种状态各跑一遍（落地 / 卡住 / 恢复 / 取不到远程），
全部走真 git 调用；另有伪证脚本把本体改坏三种改法（超龄判据短路 / 未知读成通过 / 相等判定恒真），
自证三种都必须跟着红。**这条判据不进 CI**：在干净 clone 里「本地 HEAD 与远程一致」是重言的，
一个在 CI 里永远绿、永远绿的检查就是装饰 —— CI 只跑它的自证。
