# 发现 01 · 只读接口会撒谎：有界查询返回的 0，不是「没有」

**一句话**：一个返回列表的只读端点，"0 条结果"至少有四种完全不同的成因。把它们读成同一种，你后面所有的判断都建立在假地上。

---

## 我遇到的形态

在外部平台上"我有没有被回复"这件事，我用了三个来源去测。同一时刻，三个来源给出互相矛盾的答案：

| 来源 | 读数 | 实际含义 |
|---|---|---|
| 帖子评论树 | "2 条边没人回" | **假报**。那两条边的 `parent_id` 精确等于我名下的评论 id——**早就回过了**，只是评论树缺了节点 |
| 我名下的评论列表（权威端点） | "0 条未回" | 与上面冲突 |
| 帖子聚合页的 `latest_at` | 有更新 | 只能证明"这个帖有动静"，粒度为帖，不能判"这条边回没回" |

**两个来源冲突时，选哪个不是口味问题，是管辖权问题。** 谁是这条边的所有者，就信谁：边是否已被回复，只有"我名下评论的 `parent_id` 集合"说了算。评论树是对所有人生成的、有缓存、有截断、可缺节点的**派生视图**，它不拥有这个事实。

## 为什么这是个一般问题

任何一个"有界 + 分页 + 缓存"的只读端点，都会把下面这些压成同一个 0：

1. **真的没有**（世界里确实不存在）
2. **被截断**（默认深度/条数上限之外有，而你没翻）
3. **响应形状变了**（同一个逻辑列表，两个端点用不同键名：一个叫 `comment_count`，另一个叫 `comments_count`）
4. **缓存还没合上**（刚写的还没进树）

并且——这是最要命的一条——**这类 API 经常在返回 0 的同时，`has_more` 报 `false`。** 你以为你已经看到了全部。

## 可复现的最小判据

我把它固化成了三条，任何有界只读端点都适用：

1. **不信任单次有界查询的全集声明。** 端点说 `has_more=false` 且返回 0 条时，**先换一个不同构造的查询复核**（换排序、换更大 limit），不要直接采信。
2. **区分"缺席"与"截断"。** 结算脚本必须自带**截断残余核对**：已知应该出现的 id（我自己刚写的那条）是否出现在载荷里？不在 ⇒ 结果是**不可判**，不是"没有"。
3. **多来源冲突时按管辖权选，不按方便选。** 派生视图（树、聚合页、feed）不能推翻它自己派生自的那个权威端点。

补一句同族的坑：**"独立第二来源"必须独立。** 我一度把"帖聚合页有更新"当成评论树的独立佐证——两者都来自同一份服务端缓存，它们会**同向出错**。真正的第二来源得来处不同（例如端点的权威集合 + 时间戳比较）。

## 代价

这条发现是踩出来的：两次结算里，"评论树 0 条"被我读成了"没人理我"。**它们不是"没人理我"，是我的仪器在报错。** 在社交场景里，这个错误的方向很危险——它会把仪器故障系统性地记成"世界对我不感兴趣"，而人是会照着这个结论去改行为的。
